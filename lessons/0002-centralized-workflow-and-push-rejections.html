Lesson 02: Centralized Workflow & Push Contention

🎯 Single Tangible Win for this Lesson

Understand the exact mechanics of how teams operate in a Centralized Git Workflow, why Git enforces non-fast-forward push rejections, and the scaling ceiling that forces teams to adopt Feature Branches.

1. The Centralized Topology

Before GitHub Pull Requests revolutionized software collaboration, most teams migrated to Git directly from Subversion (SVN) or Perforce. They adopted the Centralized Workflow:

  • One Central Branch: Only a single branch (main) exists on the remote server.
  • No Feature Branches: Developers commit directly to their local main branch.
  • Direct Pushes: Everyone attempts to push their local commits directly to origin/main.

2. The Non-Fast-Forward Collision

Imagine Alice and Bob both clone the project at commit C1 on Monday morning. They both work independently:

git collision sequence
1. Alice finishes first and commits C2 locally: Alice: (C1) <--- (C2) Alice runs: git push origin main -> SUCCESS! Remote main is now pointing at (C2). 2. Bob finishes his feature and commits C3 locally: Bob: (C1) <--- (C3) Bob runs: git push origin main -> FATAL REJECTION!
git push output
To https://github.com/org/repo.git ! [rejected] main -> main (non-fast-forward) error: failed to push some refs to 'https://github.com/org/repo.git' hint: Updates were rejected because the tip of your current branch is behind hint: its remote counterpart. Integrate the remote changes (e.g. 'git pull') hint: before pushing again.

3. Why Did Git Reject Bob?

Remember the law of Git's DAG from Lesson 01! A branch is a pointer to the tip of a parent chain.

For Git to allow a Fast-Forward Push, the remote commit (Alice's C2) must be a direct ancestor of Bob's commit (C3). But Bob's commit C3 points backwards to C1—it knows nothing about C2! If Git accepted Bob's push, Alice's commit C2 would be detached and lost.

4. Bob's Options: Merge vs Rebase

Option A: git pull (Merge)

Creates a diamond merge commit linking C2 and C3. Over time, the history fills with hundreds of noisy "Merge branch 'main' of github.com" commits.

Option B: git pull --rebase

Rewinds Bob's local commit C3, advances to Alice's C2, and replays Bob's change on top as C3'. Keeps history perfectly linear and clean.

5. The Scalability Ceiling

Why do teams outgrow this workflow once they grow past 2–3 developers? Push Contention Lockstep:

  • Developer A pushes. Developer B gets rejected, pulls & rebases, tests, and prepares to push.
  • While Developer B is testing, Developer C pushes! Developer B is rejected again.
  • Engineers enter a frantic "push race" to see who can rebase and push first.
