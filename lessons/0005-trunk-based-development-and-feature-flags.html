Lesson 05: Trunk-Based Development & Feature Flags

🎯 Single Tangible Win for this Lesson

Understand how elite engineering organizations (Google, Netflix, Meta) eliminate merge hell entirely by enforcing sub-24h branch lifespans and decoupling technical code deployment from business feature releases using Feature Flags.

1. The Scaling Bottleneck of Feature Branches

In Lesson 03, we studied GitHub Flow. But what happens when an engineering team grows from 10 developers to 200 developers?

If 50 feature branches live for 4 days each, the main branch moves forward by hundreds of commits every day. When each developer finally tries to merge, they face massive semantic conflicts and regression risks. Research by DORA (DevOps Research and Assessment) consistently proves: Long-lived branches are the single strongest predictor of slow delivery and high failure rates.

2. What is Trunk-Based Development (TBD)?

In Trunk-Based Development:

  • There is only one shared branch: trunk (or main).
  • Feature branches are short-lived: they live for less than 24 hours (often just 2–4 hours).
  • Every engineer integrates their work into trunk at least once a day.

3. The Grand Dilemma: "My Feature Takes 2 Weeks!"

The immediate objection every engineer raises: "I'm building an entirely new checkout workflow that takes 2 weeks. If I merge my incomplete code tomorrow, won't customers see broken UI?"

The answer is the cornerstone of modern software delivery: Decouple Deployment from Release.

feature toggle pattern
# Day 1: New UI component merged into trunk, but hidden from customers def render_checkout_page(user): if feature_flags.is_enabled("new_checkout_flow", user=user): return render_v2_checkout() # Active only for internal test accounts! return render_legacy_checkout() # Active for 100% of production traffic

4. The Power of Feature Flags

Deployment (Technical Action)

Compiling, running automated tests, and deploying code to production servers. Happens multiple times per day with zero user impact.

Release (Business Action)

Toggling the feature flag in a management dashboard (LaunchDarkly, Unleash, Statsig). Enables instant canary testing (1% -> 10% -> 100%) and instant kill-switches with zero code redeploys.

5. Branch by Abstraction

What if you are refactoring backend code (like replacing an SQL database with DynamoDB) where UI flags don't apply? You use Branch by Abstraction:

  1. Define an interface/abstraction layer around the old code. (Merge to trunk on Day 1).
  2. Write the new implementation in small commits behind the interface. (Merge to trunk daily).
  3. Switch the dependency injection binding or flag to use the new implementation. (Single atomic merge).
  4. Delete the old implementation.
