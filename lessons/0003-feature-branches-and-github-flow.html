Lesson 03: Feature Branching & GitHub Flow

🎯 Single Tangible Win for this Lesson

Understand how Feature Branching and GitHub Flow solve the push contention race of centralized development by isolating work in topic branches, enforcing peer review gates via Pull Requests, and coupling merging directly with continuous deployment.

1. The Problem GitHub Flow Solved

In Lesson 02, we saw that as soon as 3 or more engineers work on a single main branch, they run into a frantic push race. Whoever finishes first pushes, while everyone else gets rejected with non-fast-forward errors and must constantly rebase.

To eliminate this friction, GitHub introduced GitHub Flow in 2011—a lightweight, branch-and-PR model designed for web teams practicing Continuous Delivery.

2. The Branch Lifecycle

github flow lifecycle
1. Create topic branch off main: $ git checkout -b feat/stripe-billing 2. Commit small atomic units and push branch to remote: $ git push -u origin feat/stripe-billing 3. Open a Pull Request (PR) against main: - Automated CI runs: unit tests, linting, security scans - Teammates review code, leave comments, request changes 4. Merge into main upon approval & green CI: - Branch merges into main - Automated CD triggers and deploys main to production!

3. The Core Invariant: "Main is Always Deployable"

In GitHub Flow, there is no separate develop branch or staging branch. main is the single source of truth. If a commit lands on main, it must be stable, tested, and ready to ship to users immediately.

4. Pull Request Merge Strategies

When closing a PR on GitHub or GitLab, you can choose from 3 merge strategies:

Merge Commit

Preserves all WIP commits and adds a 2-parent merge commit. Shows exact chronological branch topology, but can clutter history.

Squash and Merge

Collapses 15 messy commits ("wip", "fix typo", "fix tests") into 1 pristine, atomic commit on main. Makes git bisect and reverts effortless.

5. The Anti-Pattern: Branch Aging Debt

Feature branches solve push contention, but introduce a new risk: branch aging. If a developer keeps a feature branch open for 3 weeks while 100 commits land on main, merging that branch becomes a nightmare.

⚡ Best Practice Rule of Thumb

In high-performing GitHub Flow teams, feature branches live for less than 2 days (ideally a few hours). If a feature takes 2 weeks to build, it is broken down into small, independently deployable PRs.
