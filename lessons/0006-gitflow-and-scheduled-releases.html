Lesson 06: Gitflow & Scheduled Releases

🎯 Single Tangible Win for this Lesson

Master how Gitflow orchestrates complex multi-version release cycles using two permanent branches (main and develop), and learn why the creator of Gitflow himself warned teams against using it for modern continuous web applications.

1. The World Gitflow Was Designed For

In 2010, software engineer Vincent Driessen published a blog post titled "A successful Git branching model". It quickly became known worldwide as Gitflow.

To understand Gitflow, you must understand the world of 2010: software was shipped as discrete, versioned batches (desktop installers, CD-ROMs, enterprise on-premise software, mobile apps waiting for App Store approvals). You could not continuously deploy 20 times a day to someone's desktop.

2. The Dual-Branch Spine

Instead of having just one permanent branch like GitHub Flow or Trunk-Based Development, Gitflow uses two infinite-lifetime branches:

main

Strictly reflects what is currently running in production. Only receives merges from release/* or hotfix/* branches. Every commit on main is tagged with a Semantic Version (e.g. v1.2.0).

develop

The shared staging/integration branch for developers. All feature/* branches branch off develop and merge back into develop once ready.

3. The Release Cycle: Feature Freeze & Hardening

When the team decides it is time to prepare Version 2.0, they branch off develop:

gitflow release workflow
1. Fork release branch off develop: $ git checkout -b release/2.0.0 develop 2. Feature Freeze in effect: - NO new features allowed on release/2.0.0! - Developers continue building v2.1 features on develop. - Only bug fixes, documentation, and version bumps go into release/2.0.0. 3. Complete the release: - Merge release/2.0.0 into main -> Tag: v2.0.0 - Merge release/2.0.0 into develop (so bug fixes aren't lost!) - Delete release/2.0.0 branch.

4. The Hotfix Emergency Track

What if a critical security vulnerability is found in production v2.0.0 while develop contains 50 unfinished, untested features for v2.1?

You cannot deploy develop. In Gitflow, you branch directly off main:

$ git checkout -b hotfix/2.0.1 main

You patch the bug, test it against production state, and then execute the Dual-Backport Rule:

  • Merge into main and tag v2.0.1 -> Deploy to production immediately.
  • Merge into develop -> Ensures the next release doesn't accidentally reintroduce the bug.

5. The 2020 Epilogue: Why Not Web Apps?

In 2020, Vincent Driessen added a prominent warning note to his original 2010 post:

📢 Note from the Author (2020)

"Web applications are typically delivered continuously, not rolled back, and you don’t have to support multiple versions of software running in the wild... If your team is doing continuous delivery, I suggest adopting a much simpler workflow (like GitHub Flow) instead of trying to shoehorn Gitflow into your team."

7. Check Your Understanding

Scenario Challenge

An on-call engineer fixes a severe production bug by creating branch hotfix/1.4.1 off main, tests it, merges it into main, and tags v1.4.1. Two weeks later, the team ships scheduled release v1.5.0 from develop, and the exact same bug re-appears in production! What went wrong?

💬 Socratic Reflection with Your Assistant

Notice how Gitflow maintains separate branches for different software states (main for production, develop for next release, release/* for stabilization). How does this compare to Trunk-Based Development where everything lives in a single branch and states are controlled by Feature Flags?
