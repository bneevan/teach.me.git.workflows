Reference Sheet: Gitflow Architecture & Trade-Offs

💡 The Core Gitflow Law

Gitflow introduces a dual-branch permanent spine: main strictly reflects production-released code, while develop aggregates completed features for the next release batch. Supporting branches (feature/*, release/*, hotfix/*) manage scheduled delivery lifecycles.

1. The Five Branch Types in Gitflow

1. main (Permanent)

Every commit on main is an official tagged release (e.g. v1.0.0). Developers never commit directly to main.

2. develop (Permanent)

The daily integration branch. Serves as the base for all feature branches and the origin of upcoming release branches.

3. feature/* (Temporary)

Forks off: develop
Merges back into: develop
Lifespan: Duration of feature work.

4. release/* (Temporary)

Forks off: develop
Merges back into: BOTH main AND develop
Purpose: Stabilization, version bump, bug fixes only.

5. hotfix/* (Temporary)

Forks off: main (production tag)
Merges back into: BOTH main AND develop
Purpose: Urgent production defect repair.

3. The Mandatory Dual-Backport Rule

When closing a release/* or hotfix/* branch, Gitflow strictly dictates merging into TWO places:

  1. Merge into main and tag the release version (e.g. git tag -a v1.1.1).
  2. Backport-merge into develop immediately!
⚠️ The Classic Regression Trap

If an engineer fixes an emergency bug in hotfix/1.1.1, merges it into main, but forgets to merge it into develop, the bug will re-appear in production the moment the next scheduled release (v1.2.0) deploys!

4. Architectural Trade-Off Matrix

  • Where Gitflow Excels: Traditional packaged software, mobile apps with App Store review latency, and enterprise software requiring multi-version long-term support (LTS) maintenance (e.g. maintaining v2.4 patches while developing v3.0).
  • Where Gitflow Fails (Anti-Pattern): Continuous Web Services / SaaS. Maintaining separate develop, main, and release branches creates merge overhead, slows deployment frequency to weeks, and conflicts with automated CI/CD.
