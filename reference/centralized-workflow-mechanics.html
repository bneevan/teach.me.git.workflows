Reference Sheet: Centralized Git Workflow

💡 The Centralized Model Principle

A single branch (main) acts as the central hub. Every developer works locally on main and attempts to push directly to the central remote repository.

1. The Non-Fast-Forward Conflict Cycle

push contention breakdown
1. Alice and Bob both clone commit C1: Remote main: (C1) 2. Alice commits C2 and pushes: Remote main: (C1) <--- (C2) [Alice] 3. Bob commits C3 locally and attempts to push: Bob's local: (C1) <--- (C3) Remote rejects Bob: [rejected - non-fast-forward] Because Remote's HEAD (C2) is NOT in Bob's ancestor chain!

2. Resolving the Push: Merge vs Rebase

Option A: git pull (Merge)

Creates a merge commit tying Bob's C3 and Alice's C2 together.

$ git pull origin main

Trade-off: Clutters history with repetitive "Merge branch 'main'" bubble commits.

Option B: git pull --rebase

Lifts Bob's C3 off C1 and replays it cleanly on top of Alice's C2 as C3'.

$ git pull --rebase origin main

Trade-off: Rewrites local commit hashes; requires clean working directory.

3. When is Centralized Workflow Appropriate?

  • Solo developers or pairs (1–2 developers): Zero branching overhead, instant release feedback.
  • Teams migrating from SVN: Eases the transition to distributed version control without learning branch topologies immediately.
  • When it fails: Once 3+ developers commit simultaneously, engineers spend more time resolving push-rejections and rebasing than writing code.
