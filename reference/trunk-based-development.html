Reference Sheet: Trunk-Based Development (TBD)

💡 The Core TBD Law

Merge conflicts grow super-linearly with branch lifespan. Trunk-Based Development eliminates merge debt by ensuring all branches live for less than 24 hours, continuously integrating small, tested slices into trunk.

1. The GitHub Flow vs. TBD Spectrum

GitHub Flow (Feature Branches)

Branches represent entire features and remain open until the full feature is complete (often 2–5 days). Code is deployed to production when the feature is ready.

Trunk-Based Development

Branches represent tiny sub-day increments (< 24h). Unfinished features are committed to trunk continuously behind Feature Flags.

2. Decoupling Deployment from Release

The central breakthrough of Trunk-Based Development is separating technical delivery from business exposure:

  • Deployment (Technical Action): Placing compiled, tested code onto production servers. This happens continuously multiple times a day.
  • Release (Business Action): Making that functionality visible and usable to end users. This is controlled via a dynamic Feature Flag toggle.
feature toggle pattern
def process_payment(order): # Unfinished new engine merged safely into trunk: if feature_flags.is_enabled("use_v2_stripe_engine", user=order.user): return stripe_v2_engine.charge(order) # Stable default engine for 100% of users: return legacy_engine.charge(order)

3. Branch by Abstraction: Refactoring Without Branches

How do teams replace an entire database engine or auth system without creating a 6-month stale branch? Branch by Abstraction:

  1. Create an Abstraction Layer: Wrap existing legacy calls in an interface. (Commit to trunk).
  2. Build the New Implementation: Write the new implementation class alongside the old one. (Merge small commits to trunk daily).
  3. Switch the Pointer: Update the interface factory or feature flag to point to the new implementation. (One atomic commit).
  4. Delete Legacy Code: Safely remove old code once production metrics verify stability.

4. Scaled TBD & Merge Queues

At companies like Google, Meta, and Shopify where hundreds of engineers commit every hour, a human cannot manually rebase fast enough. Teams use Merge Queues (e.g. GitHub Merge Queue, Bors):

  • PRs enter an automated queue when approved.
  • The merge robot speculatively merges PRs into trunk, runs test suites, and commits in atomic batches.
  • If a PR breaks tests, the robot ejects that PR and keeps trunk 100% green without stopping other engineers.
